## 2. 三条公开原则（本稿已按此脱敏）

1. **不出现个人身份**：真实姓名、住址、联系方式、生日、证件类信息一律不写。
2. **不出现本机环境**：绝对路径、盘符布局、机器名、凭据与配置文件内容不写；能力只用「做什么、怎么保证安全」描述。
3. **不出现内部数据**：个人信息库、会话原文、错误日志原文、费用明细不写；需要举例时用脱敏后的机制描述。

## 3. 这套体系的规模（口径：2026-11-16 实测）

- 自制插件：**27 个**在运行（其中 2 个以补丁方式挂载）；官方可选启用 12 个（2026-11-16 升级 0.2.2-rc.3 后实测：rc.3 用正式 agent-team 取代实验版 agent-team-profile，故从 13 降为 12）、第三方 3 个。
- 工作区：**5 个**，各有独立规则、验收与产出落点。
- 检查体系：**14 道门**的体检编排 + 结构/质量两闸 + 插件契约与测试门；`check` 23 条命令、`check:full` 再加结构与插件测试。
- 方法论沉淀：提问纪律、四层判据、好信息六条、闭环五件套、禁屎山、记忆分层与「检查必须能失败」。

## 4. 作者与做法（一句话背景）

非科班路线自学系统：每天一个最小闭环，错题本记「判据」而不是记答案，阶段目标以判据优先于日期（例如「五格学习法」一格一个交付物，过了验收才翻篇）。方向是 Linux 容器与网络，长期目标是运维/安全方向（SRE / DevSecOps）。这套插件与工作区就是同一套学习方法的产物：**学到的东西必须落成能红能绿的机制，否则不算学会**。

## 5. 为什么值得公开

这套东西的可迁移部分不是某一行代码，而是**判据**：怎么判断一个自动化是不是真的生效、怎么让检查敢红、怎么让记忆不膨胀、怎么让 agent 在多种工作节奏里不越界。这些都是与具体机器无关的。

## 6. 已知局限（如实标注）

- 单人维护、单人验证：所有「检查能红」的证据都来自本机运行，没有第三方复现。
- 部分能力依赖官方客户端的扩展点，随版本演进需要重新对齐（版本口径打在每个插件的说明里）。
- 记忆与评测的数字带时间窗，过期即需重测；本稿引用时都注明了日期。
